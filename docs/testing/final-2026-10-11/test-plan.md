# 提交前验收测试方案

日期：2026-10-11。目标版本为当前工作区代码与重新构建的 Docker 镜像；整个过程保留用例、执行摘要、浏览器截图和结果文档。

## 范围

覆盖题目四项业务要求：自然语言混合条件、WaveSurge候选与逐人核验/标签、结构化结果文档、Campaign目标交互。优先复测 F26–F32，并回归增量工作、持续消息、上下文、配置、认证、导出与恢复。

本轮不执行需要用户人工接管、真实平台账号登录、验证码或支付的场景。自主文字研究、公开页面和受控可访问页面可以执行。上述范围外场景不计入本轮结果和通过率。

## 三种验证资料

| 资料 | 验证用途 | 不能替代的结论 |
|---|---|---|
| 新的真实Wave数据与真实配置模型 | Instagram多组研究、全部记录补标、Campaign及只读查询；其他平台的实际可用性 | 不能保证任意画像存在20个合格账号 |
| 明确受控Wave/公开页面/图片 + 真实模型/生产任务/有头浏览器 | 确定性的分页、视觉像素、偏好、未知/否定和异常回归 | 不是这些账号在真实社交平台的发现或登录成功 |
| 历史实际反例的私有副本 + 当前生产路由/UI | F26引用、F27标签语义、F28乱序；同输入因果回归 | 不是一轮新的社交页面访问 |

两套新Compose项目采用独立数据卷，避免对主部署和开发会话产生数据污染；浏览器通过页面输入自然语言、点击方案/报告/结果/导出。特殊并发只延迟真实响应；故障场景只注入明确标记的HTTP错误，不替换成功结果。

## 判断标准

1. 业务判定以实际保存结果及模型工具回执为准，HTTP200、列表返回或高覆盖率不能代替逐人核验。
2. 每位逐条件提交理由和可追踪引用；实际画像与条件分开；未知不能变成肯定标签或入选。
3. 数量区分目标、分析预算、核验、合格、入选和缺额，多组区分记录数与去重账号数。
4. 同一请求全部已登记工作终态后交付一次；完成时间不早于任务与结果写入。刷新/正常重启不重发。
5. HTML/CSV逐条比对记录ID、任务/分组、当前入选、条件和画像；CSV使用标准解析器，不仅检查下载状态。
6. Campaign总/子/查询/弹窗/CSV与最终分配一致，原子研究预选保留审计。
7. 原题复杂画像采用明确限定的真实账号样本检查语义与证据缺口；不以小样本或受控数据宣称取得20位真实全条件正例。

## 执行顺序

自动化与新部署 → 非人工完整浏览器场景 → 新真实研究/多组补标/Campaign → 七项反例 → 原题口径和其他平台 → 逐文档/CSV核对 → 增量核验/持续消息/异常 → 最终恢复与提交文档核查。
